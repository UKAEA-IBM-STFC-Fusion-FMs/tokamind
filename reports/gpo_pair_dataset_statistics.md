## Schema Version

**Current schema:** v3 (embedding-space pairs with native diagnostics).

**Evolution:**
- v1: stored decoded native arrays — large shards, slow I/O
- v2: incremental improvements (legacy, not used)
- v3 (current): stores DCT3D / VAE embedding coefficients + scalar native diagnostics.
  Shards are 10–100× smaller than v1.

*Source: `docs/gpo_implementation_log.md §9` lines 430–442*

## Pair Source

All current collections use `pair_sources: ["model_error"]`.

A `model_error` pair is defined as:
- `y_w = z_true` — ground truth in DCT3D / VAE embedding space (preferred)
- `y_l = z_pred` — model prediction at collection time (dispreferred)
- Collected for windows where the model's prediction was measurably wrong

Each shard file (`.npz`) contains per-window records for one output signal:
- `y_w_emb` — preferred embedding coefficients
- `y_l_emb` — dispreferred embedding coefficients
- `native_nrmse` — decoded NRMSE in native signal space (for filtering at training time)
- `mse_gap` — embedding-space MSE gap (for β calibration)
- `shot_id`, `window_index` — identifiers for traceability

The `PairSource` protocol supports additional dispreferred-response generators;
no additional source is implemented yet.

*Source: `scripts_mast/mast_utils/gpo/writer.py`; `docs/gpo_implementation_log.md §13 item 2`*

## Where to find pair collections

Each task's pair collection is written into the base fine-tune run directory:

```
runs/ft-<task>-scratch-mmt-<BASE_TAG>/gpo_pairs_<GPO_TAG>/
  ├── <signal>__shard_000000.npz   ← pair data
  ├── <signal>__shard_000001.npz
  ├── ...
  ├── metadata.json                ← schema version, task, total_windows per signal
  ├── collection_config.json       ← run_id, split, pair_sources
  └── stats_report.html            ← interactive stats (if generated)
```

The number of shards and window counts per signal vary by task and depend on:
- The size of the training split
- How often the model makes a measurable error (pair density)
- The `native_nrmse_percentiles` and `max_pairs_per_shot_percentile` filters

*Source: `scripts_mast/mast_utils/gpo/writer.py`; `scripts_mast/run_collect_gpo_pairs.py`*

## Active Training-Time Filters (v8 — all tasks)

Applied by `GpoPairDataset` when loading pairs during GPO training (not at collection time):

| Filter | All tasks | Notes |
|--------|-----------|-------|
| `native_nrmse_percentiles: [25.0, 95.0]` | ✓ | Remove trivially-solved (p0–25) and extreme-outlier (p95–100) pairs |
| `max_pairs_per_shot_percentile: 90.0` | ✓ | Cap over-represented shots at p90 of per-shot window-count distribution |
| `shot_blacklist` | task-specific | Catastrophic outlier shots identified from panel 23 (outlier table) |
| `min_window_index` | task-specific | Skip early ramp-up windows (e.g., first 50 for task_4-5) |
| `mse_gap_clip` | task-specific | Hard-clip on embedding MSE gap (e.g., 50.0 for task_4-5) |
| `log_mse_gap` | task-specific | `log(1 + MSE)` compression (e.g., task_4-5 fat tail) |

*Source: `gpo_tasks.yaml` lines 83–691; `docs/gpo_implementation_log.md §11` lines 495–553*

## Collection split and val fraction

- **Collection split:** Train split of MAST dataset (model sees test split only during eval).
- **GPO val fraction:** 10% of collected pairs held out for GPO validation (`GPO_VAL_FRACTION=0.1`).
  This val set is used for early stopping during GPO training — it is distinct from the
  MAST test split used for NRMSE evaluation.

*Source: `docs/gpo_runbook.md §Environment variables`; `cluster/ccc_collect_gpo_pairs.sh`*
